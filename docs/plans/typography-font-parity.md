# Typography #3: font and text parity across browser, SVG and PNG

## Problem, evidence and impact

The engine renders the same document through three paths that use two different font engines. `src/render.ts` receives its measurer as a parameter: the workbench passes `browserMeasure()` (Blink `canvas.measureText`), while `scripts/benchmark.ts` and `scripts/verify.ts` pass the napi-rs/Skia measurer from `scripts/native.ts`. `renderPng` measures and draws with the same Skia context, so it can be wrong but never disagrees with itself. Standalone SVG is the opposite: its line breaks and `<tspan>` positions are computed from Skia metrics, but its glyphs are drawn later by whatever viewer opens the file. Nothing in the repository compares these paths, so a disagreement becomes visible only as a clipped or rewrapped export after the fact.

Five specific findings motivate this task. All were observed on the current `main` (`9070582`).

1. **The browser has more glyph coverage than the native renderer.** `src/main.ts` imports `@fontsource/inter/400.css`, `500.css`, `600.css`, `700.css` and `@fontsource/source-serif-4/600.css`. Those stylesheets register seven Inter subset files per weight (latin, latin-ext, cyrillic, cyrillic-ext, greek, greek-ext, vietnamese) and six Source Serif 4 subsets. `scripts/native.ts` registers only `inter-latin-<weight>-normal.woff2` and `source-serif-4-latin-600-normal.woff2`. Latin-ext, Cyrillic, Greek and Vietnamese text therefore measures and renders correctly in the browser and silently falls back to a Skia default font in the native PNG and in standalone-SVG layout. Different advance widths produce different line breaks, which can clip content that previewed cleanly.

2. **A shipped fixture already depends on an uncovered glyph.** `ticket-label` in `src/fixtures.ts` reads `SAVE YOUR SEAT  →` and contains U+2192. No Inter subset in the fontsource build covers U+2192; the latin subset's `unicode-range` lists U+2191 and U+2193 only. Every renderer substitutes its own fallback for that one character, with no diagnostic anywhere. This is not a contrived probe — it is in the design shown by default when the workbench opens.

3. **`supportsFont` cannot express this class of failure.** `src/resources.ts` validates `(family, weight)` against a five-entry allow-list and never sees the text being rendered. A design using `fontFamily: 'Inter'` with Arabic, CJK or emoji content passes `validateResources` unchanged and reaches the measurer, where coverage is resolved silently and differently per engine. `docs/design-contract.md` already states that a `supportsFont` declaration "does not prove full multilingual glyph coverage" and assigns glyph-coverage validation to the host; for `BUNDLED_RESOURCES` this repository is that host, and the validation does not exist yet.

4. **Rendered whitespace is normalized and undocumented.** `layoutText` builds words with `paragraph.split(/\s+/).filter(Boolean)`, so runs of spaces and tabs collapse to a single separator and leading/trailing whitespace is dropped from rendered lines. `e.text` is never mutated, so the document preservation contract holds, but the rendered result does not reproduce the source spacing. No test pins this and no document states it.

5. **Bidirectional text is unhandled rather than declared unsupported.** `layoutText` splits on whitespace and `render.ts` emits left-to-right positioned `<tspan>`s with no `direction` or `unicode-bidi`, so RTL content would render in incorrect visual order even if a font covered it.

Impact: the workbench preview can disagree with the exported PNG and SVG; "supported font" currently means "family and weight are registered", not "these glyphs can be drawn"; and issues #5 and #6 are waiting on typography constraints that cannot be stated honestly until coverage and parity are measured.

## Intended behavior and approach

- **Coverage is derived, not hand-maintained.** A new `src/font-coverage.ts` holds the bundled families' supported codepoint ranges, generated from the `unicode-range` declarations that fontsource ships in its stylesheets, together with a `findUncoveredText(design)` helper returning the offending element IDs and codepoints. A test regenerates the table from `node_modules/@fontsource/**` and fails if the committed constant has drifted, so a dependency bump cannot silently invalidate the declaration.
- **Uncovered content is reported as a warning, not a hard error.** A new additive `Finding` kind `unsupported-glyph` (severity `warning`) is emitted by `evaluate`, so uncovered characters surface in the workbench issue overlay, `npm run verify` and the benchmark report. A hard `resource` error is deliberately not used: the currently shipping `→` fixture would turn 30 benchmark cases red and block the team on a cosmetic glyph, and the repository's principle is to keep failures visible rather than to refuse valid-looking work. Existing error kinds, thresholds and selection behavior stay unchanged.
- **RTL and complex scripts are declared unsupported explicitly.** Text containing RTL codepoints produces the same `unsupported-glyph` finding with a message naming bidirectional text as unsupported, rather than being silently reordered.
- **Native registration matches the browser.** `scripts/native.ts` registers every subset file the corresponding fontsource stylesheet loads, not just the latin subset, so Skia and Blink resolve the same families over the same coverage. Registration remains explicit and still throws when a file is missing.
- **Parity is asserted on line breaks, not only on widths.** Advance widths from two engines will never match exactly, so the binding assertion is that `layoutText` produces an identical `lines` array under both measurers for the same element; width, ascent and descent deltas are recorded as observational evidence with their observed maxima, not turned into an invented tolerance.
- **The comparison runs where a real browser exists.** `scripts/font-parity.ts` writes native metrics for a fixed probe corpus to `reports/font-parity/native-metrics.json`; `tests/browser-checks.ts` fetches that file from the dev server and compares it against live browser measurements. The probe corpus covers every text element of the ten fixtures across the three targets plus documented cases: a long unbroken word, explicit line breaks, repeated whitespace, combining marks, an emoji sequence with a ZWJ, and a small labelled non-Latin and RTL sample.

## Risks

- Registering additional native subsets changes measured widths for any text containing latin-ext characters, which can change line breaks and therefore candidate selection. The benchmark diff must be reported honestly rather than presented as a no-op.
- The coverage table is derived from fontsource's declared `unicode-range`, which describes how Google subsetted the files. It is a strong proxy for the files' contents but is not a `cmap` read; a font whose declared range overstates its contents would not be detected.
- A warning-severity finding does not prevent a mismatched export. It makes the condition visible; it does not make non-Latin text render correctly, and must not be described as multilingual support.
- Browser measurements depend on the browser, platform and font rasterization settings of whoever runs `/verify.html`. The recorded deltas are evidence from one environment, not a cross-platform guarantee, and the report must name the browser and version.
- Emoji rendering depends on a colour font supplied by the operating system in the browser and absent in Skia. Emoji will be reported as uncovered; that is the intended honest result, not a regression to fix here.
- Line-break equality across engines may prove unattainable for some strings even within covered ranges. If so, record the specific failures and the deltas that cause them rather than relaxing the assertion until it passes.

## Execution record

Completed September 19, 2026. Full measurements and data: [dated evidence](../evidence/2026-09-19-typography-parity/README.md).

- Base: `8a2568c`. The tree moved during the task — an agent ran `git pull`, fast-forwarding from `9070582` and bringing in the corpus validator (#7), measurement cache (#8) and a Playwright browser harness. The plan's findings were re-verified against the new tree and all held: `scripts/native.ts` still registered latin subsets only, `src/typography.ts` was unchanged, and the `→` was still in `src/fixtures.ts`. The Playwright harness improved the outcome — the new cross-renderer check is CI-gated rather than needing a manual `/verify.html` visit.
- **The plan's central assumption was wrong.** It proposed registering every subset file under its family name so Skia and Blink would resolve the same coverage. `GlobalFonts.registerFromPath` consults only the first registration per `(family, weight)`; registering all seven Inter subsets under `'Inter'` measured identically to registering `latin` alone. A comma-separated fallback list also fails, shaping a whole string with one font chosen from its leading character. The implementation registers each subset under a private alias and measures/draws in runs by covering subset.
- Red evidence: `tests/native-font-registration.test.ts` failed 5/7 against unmodified `native.ts`, with Cyrillic/Greek/Vietnamese/latin-ext measured through Skia's default fallback. `tests/typography-parity.test.ts` failed on a missing `src/font-coverage.ts`. `tests/unsupported-glyph.test.ts` failed 3/4 with the finding kind absent, its ASCII positive control already passing.
- The coverage helper deliberately does **not** flag Cyrillic or Greek. Those scripts are inside Inter's declared coverage; the divergence was native registration, not the font. Flagging them would have been factually wrong and would have failed the positive-control requirement.
- `unsupported-glyph` is emitted from the output design only, once per `Metrics`, rather than from source and candidate both.
- **Line-break parity failed on one probe, and the root cause was fixed rather than quarantined.** `product-pairs/story/headline` sat 0.005px inside its box, so Chromium and Skia wrapped `"everyday."` differently. Widening `fitText`'s `+0.01px` epsilon — the first proposal — would have worsened it, since that epsilon admits overflow while the search still converges onto the boundary. `fitText` now fits against `width × (1 − 0.005)`.
- **The clearance was sized twice.** An initial 0.05% was derived from that single probe. Measuring the whole corpus afterwards showed relative width deltas reaching 0.2856% on strings dense with kern pairs — 5.7× that value — so the first figure was under-dimensioned and was corrected to 0.5%, the smallest tested clearance surviving 0.3% injected noise. Cost at 0.5%: one element of 141 refits, losing 0.48px of font size.
- Final: **241 tests**, build, `npm run verify` (30 layouts), and `npm run verify:browser` (12/12 checks, **150/150 probes agreeing on line breaks**) all pass. Both fault injections fail as required.
- Benchmark against unmodified `main`: 69 of 70 PNGs and 69 of 70 design JSONs byte-identical; the one changed output differs by a single `fontSize` line. Errors stay 0/0/0 and candidate selection is unchanged. Warnings rise 42→45 baseline and 11→14 selected, entirely from the pre-existing `ticket-label` arrow.
- Two defects were found and fixed in passing: `tests/browser/acceptance.spec.ts` hardcoded `?fault=separate-badge`, so any third fault name would never have reached the page; and the workbench summary described all warnings as "readability warnings", which the new finding is not.
- Reported but not asserted: the browser report's headline `maxWidthDelta` of 883px is a probe artifact from whole-string measurement of text containing `\n`, which layout never performs. The evidence separates that, and declared-uncovered content, from the 105 supported single-line probes that carry the real parity result.
- Remaining: the `ticket-label` arrow disposition is a shared-fixture decision for the engine owner, and the `unsupported-glyph` findings need review by whoever owns `src/fixtures.ts`. Skill assessment: no new skill created — the repository's plans, tests and verification scripts already capture this workflow.
